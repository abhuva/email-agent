# Product Design Document (PDD): V6 Database Core

*   **Status:** `Approved`
*   **Version:** 1.1 (Final)
*   **Author(s):** Marc Bielert (Dev) & Strata (AI Strategist)

---

## 1. Overview & Strategy (The "Why")

*   **Executive Summary:** This project will re-architect the Email Agent's data layer, migrating the source of truth from individual Markdown files to a centralized SQLite database. This foundational change will resolve critical performance bottlenecks at scale and unlock powerful new capabilities for data analysis and future feature development.

*   **Problem Statement:** As the system scales beyond 10,000 entries, the current file-based architecture has introduced significant performance bottlenecks, making essential operations like reprocessing computationally expensive and slow. Furthermore, this architecture fundamentally limits the system's potential by preventing advanced, cross-entry analysis (e.g., email thread reconstruction) and tightly coupling the data model to a single output format (Markdown), blocking future applications.

*   **Strategic Alignment:** This project directly supports the strategic evolution of the Email Agent from a linear note-generation tool into a robust personal intelligence platform. Establishing a database core is the necessary prerequisite for enabling future high-value features, improving system scalability, and decoupling data ingestion from data presentation, thereby increasing analytical power and development velocity.

## 2. The User & The Goal (The "Who" and "What Success Looks Like")

*   **Target Audience / User Personas:** The Developer (Primary).
*   **Goals & Success Metrics:** The success of the V6 architectural migration will be measured by the successful implementation of a decoupled, three-stage command structure.

    *   **Product Goals (Architectural Decoupling):**
        1.  **`pull` Command:** A new command that exclusively handles data ingestion, fetching new emails and writing their raw content and metadata into the database.
        2.  **`process` Command:** A new command that handles data transformation, querying the database based on filters, running matching entries through the LLM and rules engine, and writing the results back to the database.
        3.  **`output` Command:** A new command that handles data presentation, querying the database for processed entries and generating final markdown notes.

    *   **Counter-Metrics (Critical Constraints):**
        1.  **Data Fidelity:** The markdown files generated by the new `output` command must be functionally equivalent to those generated by the V5 system.
        2.  **Idempotency (Critical):** Running the `pull` command multiple times must **not** create duplicate email entries in the database.

## 3. Scope & Requirements (The "What")

*   **Scope & Boundaries (CRITICAL):**
    *   **In-Scope:** A foundational SQLite database (`email.db`); new CLI commands (`db-init`, `pull`, `process`, `output`); a V1 database schema; a documented process for manual schema migration scripts.
    *   **Out-of-Scope:** Migration of existing Markdown notes; new analysis features (e.g., threading); alternative output formats; automated migration frameworks (e.g., Alembic); performance-only optimizations.

*   **User Stories / Job Stories:**

    *   **Story 0: `db-init` Command (Bootstrapping):**
        *   **As a** Developer, **I want to** run a `db-init` command, **so that** I can create and initialize the database with the correct V1 schema on a new system.
        *   **Acceptance Criteria:**
            1.  A command `main.py db-init` exists.
            2.  If `email.db` does not exist, it is created.
            3.  The command executes `CREATE TABLE` statements to build the `emails` table as defined in the V1 schema.
            4.  If the table already exists, the command should notify the user and exit gracefully without making changes.

    *   **Story 1: `pull` Command (Ingestion):**
        *   **As a** Developer, **I want to** run a `pull` command, **so that** I can populate the database with new emails based on specific filters.
        *   **Acceptance Criteria:**
            1.  Supports filtering by `--account <name>`, `--all`, `--after <date>`, and `--before <date>`.
            2.  Checks for duplicates using an `account_name` + `IMAP UID` composite key before inserting.
            3.  Stores raw email data (headers, body, attachment metadata) in the `emails` table.
            4.  Does **not** call the LLM API or generate files.

    *   **Story 2: `process` Command (Enrichment):**
        *   **As a** Developer, **I want to** run a `process` command, **so that** I can apply business logic and LLM classification to emails in the database.
        *   **Acceptance Criteria:**
            1.  Queries the DB based on filters to find records needing processing (e.g., `status = 'new'`).
            2.  For each record, applies the **blacklist rules engine**.
            3.  If not blacklisted, sends to the **LLM API** for scoring/summarization.
            4.  Applies the **whitelist rules engine** to adjust results.
            5.  Updates the record with results, a `processed_at` timestamp, and a `status` of `'processed'`.
            6.  In case of failure, updates the record with `status = 'processing_failed'`, and populates `error_stage` and `error_message` fields before continuing.

    *   **Story 3: `output` Command (Presentation):**
        *   **As a** Developer, **I want to** run an `output` command, **so that** I can generate markdown notes from the processed data.
        *   **Acceptance Criteria:**
            1.  Queries the DB for processed records based on filters.
            2.  Uses existing V5 `note_generator` logic to create Markdown files.
            3.  Overwrites existing files to ensure they reflect the latest database state.

## 4. Design & User Experience (UX)

*   **User Flow:** The user will interact with the system via four distinct CLI commands. The typical workflow is:
    1.  `db-init` (once per system)
    2.  `pull` (to ingest data)
    3.  `process` (to enrich data)
    4.  `output` (to view data)
*   **Deprecation:** The monolithic V5 `process` command is deprecated.

## 5. Technical & Non-Functional Requirements

*   **Database Schema (V1 - `emails` table):**
    *   **Primary Key:** `id` (INTEGER, AUTOINCREMENT).
    *   **Business/Unique Key:** A composite `UNIQUE` constraint on `(account, imap_uid)`.
    *   **Data Columns:** `account`, `imap_uid`, `headers` (JSON), `body_raw`, `attachment_meta` (JSON), `status`, `llm_summary`, `llm_scores` (JSON), `llm_tags` (JSON), `created_at`, `processed_at`, `error_stage` (TEXT, Nullable), `error_message` (TEXT, Nullable).
    *   **Indexes:** An index on `(account)` and another on `(status, processed_at)`.

*   **Schema Migration Procedure (MANDATORY):**
    1.  **Stop Application:** Ensure the main application is not running.
    2.  **Write Migration Script:** Create a new script in `scripts/migrations/` (e.g., `001_add_thread_id.py`). This script must connect to the database and perform `ALTER TABLE` operations. New columns should be added as `NULLABLE` to avoid breaking existing `INSERT` statements.
    3.  **Run Script:** Manually execute the migration script to apply the schema change.
    4.  **Update Application Code:** Modify the application code (e.g., database models, queries) to recognize and utilize the new schema.
    5.  **Test:** Run the application and its tests to confirm compatibility with the new schema.
    6.  **Commit:** Commit both the migration script and the application code changes together.

## 6. Go-Live Plan & Future Work

*   **Future Iterations (The "Why" for V6):**
    1.  **Web Interface:** Building a local web application to browse and search the email database.
    2.  **Deep Obsidian Integration:** Creating a plugin to trigger commands directly from the Obsidian UI.
    3.  **Advanced Analysis Engine:** Implementing email threading, link extraction, and other advanced analytics.

*   **Open Questions & Risks:**
    *   **Risk:** Performance at Extreme Scale (e.g., 500k+ records).
        *   **Mitigation:** **Accepted Risk.** We will not prematurely optimize. If SQLite becomes a bottleneck in the future, we will plan a migration to a more robust database.
    *   **Risk:** N+1 Query pattern in `pull` command's duplicate check.
        *   **Mitigation:** **Accepted Risk.** We are knowingly accepting this trade-off in V1 in favor of implementation simplicity and maintaining full developer control over filters.

*   **Decision Log:**
    *   **Schema Evolution:** The database is the **source of truth**. We will use **manual migration scripts** to preserve data during schema changes.
    *   **Generated File Handling:** Markdown files generated by `output` are **disposable, read-only artifacts**. Manual edits will be overwritten.
    *   **Bootstrap Process:** The system will use an explicit `db-init` command for initial database and schema creation.
